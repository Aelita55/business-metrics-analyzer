# ADR-004. Кэширование KPI через Redis

## Статус

Принято.

## Контекст

Требование AD-01: время отклика дашборда — не более 3 секунд. Расчёт KPI может быть ресурсоёмким при большом объёме данных о продажах. Дашборд должен быстро отдавать агрегированные показатели.

## Решение

Использовать Redis как кэш для KPI и агрегатов дашборда.

Планируемая схема:
- ключи кэша формируются по периоду, набору метрик и роли/фильтрам;
- TTL задаётся в зависимости от типа метрики;
- при импорте новых данных или изменении справочников выполняется инвалидация соответствующих ключей;
- при недоступности Redis система продолжает работать с PostgreSQL.

## Альтернативы

1. Без кэша — проще, но риск не уложиться в 3 секунды при больших объёмах.
2. Materialized views в PostgreSQL — полезно для тяжёлых агрегатов, но сложнее в оперативном обновлении.
3. In-memory кэш внутри приложения — не подходит для нескольких экземпляров приложения.
4. Отдельное KPI-хранилище — избыточно для MVP.

## Последствия

Плюсы:
- снижение времени отклика дашборда;
- уменьшение нагрузки на PostgreSQL;
- гибкое управление TTL и инвалидацией.

Минусы:
- дополнительный инфраструктурный компонент;
- необходимость продумать инвалидацию кэша;
- возможна временная несогласованность данных.
