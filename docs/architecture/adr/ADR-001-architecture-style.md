# ADR-001. Выбор архитектурного стиля

## Статус

Принято.

## Контекст

Проект «Business Metrics Analyzer» разрабатывается командой из 3–4 человек. Требуется быстро выпустить MVP веб-приложения для расчёта и визуализации KPI торговой компании. При этом система должна иметь возможность последующего масштабирования и выделения отдельных сервисов.

Ключевые требования:
- быстрый MVP;
- разграничение ролей;
- импорт до 1 млн записей;
- время отклика дашборда ≤ 3 с;
- развёртывание в Docker в облаке.

## Решение

Выбран слоистый монолит с элементами Clean Architecture.

Структура слоёв:
- Presentation;
- Application;
- Domain;
- Infrastructure.

Бизнес-логика размещается в Application и Domain слоях и не зависит напрямую от FastAPI, SQLAlchemy и внешних сервисов.

## Альтернативы

1. Микросервисы — избыточны для MVP, требуют сложной инфраструктуры, orchestration, распределённых транзакций и зрелого DevOps.
2. Монолит без слоёв — быстрый старт, но высокая связанность, сложность тестирования и сопровождения.
3. Serverless — ограничения по времени выполнения и холодному старту для batch-импорта до 1 млн записей.
4. Clean Architecture в полном объёме — даёт хорошую изоляцию, но может замедлить MVP из-за избыточной формализации.

## Последствия

Плюсы:
- быстрая разработка и развёртывание;
- понятное разделение ответственности;
- упрощённое тестирование бизнес-логики;
- возможность поэтапного выделения сервисов.

Минусы:
- ограниченная горизонтальная масштабируемость;
- необходимость рефакторинга при переходе к микросервисам;
- риск «разрастания» монолита при недостаточной дисциплине слоёв.
