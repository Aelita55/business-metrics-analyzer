# ADR-005. Асинхронный импорт данных

## Статус

Принято.

## Контекст

Система должна поддерживать импорт данных о продажах из CSV/Excel и внешних источников. Объём — до 1 млн записей. Синхронный импорт в HTTP-запросе может привести к таймаутам и блокировке API.

## Решение

Использовать асинхронную обработку импорта.

Для MVP:
- HTTP-запрос создаёт задачу импорта и возвращает идентификатор;
- обработка выполняется фоновым worker-процессом;
- данные читаются и валидируются чанками;
- запись выполняется batch-вставками через Repository + Unit of Work;
- статус импорта доступен через API.

В дальнейшем можно вынести обработку в очередь сообщений и отдельный сервис.

## Альтернативы

1. Синхронный импорт — проще, но риск таймаутов и плохой UX при больших файлах.
2. Внешний ETL-инструмент — избыточен для MVP.
3. Полноценная очередь сообщений с первого дня — увеличивает сложность инфраструктуры.
4. Ручная загрузка через БД — не соответствует бизнес-требованиям.

## Последствия

Плюсы:
- API остаётся отзывчивым;
- большие файлы обрабатываются без таймаутов;
- можно показывать прогресс и ошибки импорта;
- архитектура готова к выделению отдельного сервиса импорта.

Минусы:
- усложняется обработка ошибок и статусов;
- требуется worker-процесс;
- возможна задержка между загрузкой файла и появлением данных в дашборде.
